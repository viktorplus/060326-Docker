## Проект (project)

Запуск Compose — это не «просто контейнеры», а **проект**: 
* конкретное развёртывание спецификации на платформе.

Имя проекта задаётся:

- полем `name:` в файле;
- флагом `-p` / переменной `COMPOSE_PROJECT_NAME`;
- иначе — именем каталога.

От имени проекта зависят имена всех 
* контейнеров, 
* сетей 
* томов 
* и т.д.



## Compose-файл

Основное имя Compose-файла по умолчанию — `compose.yaml`.
Также поддерживаются:
- `compose.yml`;
- `docker-compose.yaml`;
- `docker-compose.yml`.


Иначе — надо специально указывать имя файла при запуске:

```bash
docker compose -f my_docker_compose_file.yaml up
```

Ключ `version:` в современных файлах **не нужен** (форматы 2.x/3.x слиты в Compose Specification). 
Его часто оставляют по привычке; реализация его игнорирует.

Минимальная схема:

```yaml
services:          # обязательный раздел
  web:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - db
  db:
    image: postgres:16
    volumes:
      - db_data:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: example

volumes:
  db_data:

# networks:   — опционально; иначе будет default
```

Несколько файлов можно объединять (`-f compose.yaml -f compose.override.yaml`). 
Есть `include` для модульности.

Типичные поля сервиса:

| Идея                       | Зачем                                                                                                            |
|----------------------------|------------------------------------------------------------------------------------------------------------------|
| `image` / `build`          | готовый образ или сборка из Dockerfile                                                                           |
| `ports`                    | публикация на хост (`HOST:CONTAINER`)                                                                            |
| `expose`                   | порт только внутри сети Compose                                                                                  |
| `environment` / `env_file` | переменные внутри контейнера                                                                                     |
| `volumes`                  | данные и код                                                                                                     |
| `depends_on`               | порядок *создания/старта*, не «приложение уже готово принимать запросы»                                          |
| `healthcheck`              | критерий готовности; с `depends_on: condition: service_healthy` уже ближе к реальной зависимости                 |
| `restart`                  | политика перезапуска                                                                                             |
| `command` / `entrypoint`   | переопределение запуска                                                                                          |


Важный теоретический нюанс: **`depends_on` сам по себе не ждёт готовности БД**.  
Он гарантирует, что контейнер `db` стартовал раньше `web`.  
Приложение внутри `db` может ещё инициализироваться.  
Для этого используют healthcheck, скрипты ожидания или init-контейнеры.


## Как это работает при `docker compose up`

Упрощённый цикл:

1. Найти и разобрать файл(ы), подставить переменные (`${VAR}`, файл `.env` рядом с проектом).
2. Определить имя проекта и набор ресурсов.
3. Собрать образы (`build`) и/или скачать (`pull`).
4. Создать сети и тома.
5. Создать и запустить контейнеры сервисов с учётом зависимостей.
6. Подключить сервисы к сетям → заработает DNS по имени сервиса.

`up` стремится к желаемому состоянию.  
`down` останавливает и убирает контейнеры и сети проекта (тома по умолчанию **сохраняет**, пока не укажете `-v`).


## Основные команды жизненного цикла

- `docker compose up` / `up -d` — создать и запустить  
- `docker compose down` — остановить и удалить контейнеры и сети  
- `docker compose ps` — состояние сервисов  
- `docker compose logs -f` — логи  
- `docker compose build` — пересборка  
- `docker compose pull` — обновить образы  
- `docker compose exec SERVICE CMD` — команда в уже работающем контейнере  
- `docker compose run SERVICE CMD` — разовый контейнер сервиса (удобно для миграций)  

Проект можно указать явно: `docker compose -f path/compose.yaml -p myproj up -d`.


### Переменные и окружения

Compose подставляет `${VAR}` из окружения процесса и из `.env` в каталоге проекта 
(это **не** то же самое, что `env_file` внутри сервиса).

- `.env` рядом с Compose — для интерполяции самого YAML (`ports: "${APP_PORT}:80"`).
- `environment` / `env_file` у сервиса — то, что увидит процесс *внутри* контейнера.



#### Пример `.env` + environment

* `.env`:
```dotenv
POSTGRES_USER=admin
POSTGRES_PASSWORD=secret123
POSTGRES_DB=mydb
```

* `docker-compose.yml`:
```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
```      

#### Пример `env_file` 

Здесь Compose не подставляет значения в YAML, а непосредственно передаёт переменные из db.env в окружение контейнера.

* `db.env`:
```dotenv
POSTGRES_USER=admin
POSTGRES_PASSWORD=secret123
POSTGRES_DB=mydb
```

* `docker-compose.yml`:
```yaml
services:
  db:
    image: postgres:17
    env_file:
      - db.env
```

Имя файла `db.env` может быть любым, главное, чтобы совпадало с именем, указанным в `env_file`.


## Границы применимости

Compose хорошо закрывает:

- локальную разработку полного стека;
- интеграционные тесты;
- простые стенды и один сервер.

Compose **не даёт** из коробки то, ради чего используют оркестраторы:

- планирование по многим нодам;
- самовосстановление как у контроллеров K8s;
- сложные `rolling update` / `service mesh` на уровне кластера.


## Резюме

1. Приложение = набор **сервисов** + **сети** + **тома**.  
2. Файл — декларация желаемого состояния, проект — конкретный экземпляр.  
3. Сервисы находят друг друга по **имени сервиса** в общей сети.  
4. Данные, которые должны пережить контейнер, живут в **томах**.  
5. Порядок старта ≠ готовность приложения; для готовности нужны healthcheck/ожидание.
