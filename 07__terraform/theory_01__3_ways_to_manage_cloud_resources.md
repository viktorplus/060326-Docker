# Три способа управления облачными ресурсами

Облачные платформы (AWS, Microsoft Azure и Google Cloud) предоставляют несколько способов создания, настройки и управления ресурсами.

Можно выделить три основных подхода:

1. **Графический** — управление через веб-интерфейс облачного провайдера.
2. **Императивный** — управление с помощью команд, например AWS CLI.
3. **Декларативный** — описание желаемого состояния инфраструктуры с помощью Terraform.


## 1. Графическое управление (GUI)

### Принцип работы

Пользователь взаимодействует с облачной инфраструктурой через **графический интерфейс**. 

Например, типичный процесс создания виртуальной машины в AWS:

1. Открыть AWS Management Console.
2. Перейти в сервис EC2.
3. Нажать Launch instance.
4. Указать имя виртуальной машины.
5. Выбрать операционную систему и тип экземпляра.
6. Настроить сетевые параметры и правила доступа.
7. Настроить диск.
8. Добавить исполняемый скрипт (опционально)
9. Нажать `Launch instance`.


### Особенности

Графический интерфейс позволяет работать с инфраструктурой без написания команд и программного кода.

Пользователь вручную выполняет последовательность действий в интерфейсе.

**Преимущества**:

- Низкий порог входа.
- Наглядное представление ресурсов и их состояния.
- Удобство первоначального знакомства с облачной платформой.
- Возможность быстро выполнять разовые операции.
- Удобная визуальная диагностика некоторых проблем.

**Недостатки**:

- Трудно автоматизировать повторяющиеся операции.
- Сложно воспроизвести одну и ту же конфигурацию в разных окружениях.
- При большом количестве ресурсов ручное управление становится трудоёмким.
- Историю изменений и текущую конфигурацию сложнее поддерживать в виде единого описания инфраструктуры.
- Возникает риск человеческой ошибки.

### Когда использовать

Графический интерфейс особенно полезен:

- При первоначальном изучении облачной платформы.
- При исследовании доступных сервисов и их параметров.
- При выполнении разовых административных операций.
- При визуальной диагностике состояния ресурсов.

Однако при регулярном управлении инфраструктурой обычно удобнее использовать программные инструменты.

## 2. Императивное управление (`AWS CLI`)

### Принцип работы

Императивный подход предполагает, что пользователь даёт системе точные указания **что и как делать**.

`AWS CLI (Command Line Interface)` — инструмент командной строки, позволяющий управлять ресурсами AWS.

Вместо перехода по страницам веб-интерфейса пользователь выполняет команды в терминале.


### Пример: создание виртуальной машины

Прошлый раз мы создали команду, в которой подробно перечислены конкретные действия: 
* [создать один экземпляр EC2 с заданными параметрами.](../06__AWS_Exploring__AWS_CLI__Boto_3/theory_04__creation_new_using_AWS_CLI.md)


```bash
aws ec2 run-instances \
    --image-id ami-09903cd4fe0670a06 \
    --count 1 \
    --instance-type t3.micro \
    --key-name AWS_key \
    --associate-public-ip-address \
    --security-group-ids sg-00852e8407c919d4a \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=voting_app_GROUP_NAME}]' \
    --region eu-central-1 \
    --user-data file://my-voting-app.sh
```

### Особенности императивного подхода

(Императивный — важно **как**, а не **что**).

В императивной модели пользователь скрупулёзно описывает последовательность необходимых действий.


### Преимущества

- Возможность автоматизировать управление ресурсами.
- Удобство выполнения повторяющихся операций.
- Возможность объединять команды в скрипты.
- Интеграция с CI/CD.
- Доступ ко многим операциям облачной платформы без использования графического интерфейса.

### Недостатки

- Необходимо самостоятельно описывать последовательность действий.
- Нужно учитывать зависимости между ресурсами.
- Повторный запуск некоторых команд может приводить к нежелательным изменениям или созданию дополнительных ресурсов.
- Поддержка сложной инфраструктуры требует дополнительной логики.


### Выводы

- Императивный подход удобен для автоматизации повторяющихся действий.  
- Однако требует внимания к деталям, которые надо прописать вручную.
- Иногда за лесом **как сделать** можно не увидеть **что именно** ожидается получить в итоге.


Возникает закономерный вопрос: 
- обязательно ли каждый раз самостоятельно определять последовательность операций?

Именно здесь становится полезен декларативный подход.

## 3. Декларативное управление (`Terraform`)

(Декларативный — важно **что** и не важно **как**).


### Принцип работы

Декларативный подход предполагает, что пользователь описывает желаемое состояние инфраструктуры.

А каким образом это будет выполняться — определяет уже сам инструмент.

**Terraform** — инструмент Infrastructure as Code (IaC), позволяющий 
* описывать желаемую облачную инфраструктуру 
* с помощью конфигурационных файлов.

Terraform самостоятельно 
* сравнивает описанную конфигурацию с известным ему текущим состоянием ресурсов 
* и осуществляет необходимые изменения.


### Преимущества

- Инфраструктура описывается в виде кода.
- Конфигурацию можно хранить в Git.
- Изменения можно анализировать до применения.
- Terraform автоматически определяет многие зависимости между ресурсами.
- Повторное применение неизменённой конфигурации обычно не приводит к созданию дубликатов.
- Можно воспроизводить инфраструктуру в разных окружениях.
- Удобно использовать в CI/CD.
- Поддерживается управление ресурсами разных облачных провайдеров.

### Недостатки

- Необходимо изучить синтаксис HCL и принципы работы Terraform.
- Требуется управлять состоянием инфраструктуры.
- Не все параметры ресурсов можно менять без их пересоздания.
- Terraform не устраняет необходимость понимать устройство облачной платформы.
- Terraform не выполняет абсолютно все операции AWS CLI. 
  - (Некоторые возможности AWS CLI могут быть недоступны в Terraform Provider)
- Terraform не гарантирует, что фактическая инфраструктура всегда будет соответствовать конфигурации. 
  - (Ошибки, ограничения API и другие обстоятельства могут привести к расхождениям)

### Когда использовать

Terraform особенно полезен, когда необходимо:

- Создавать сложную инфраструктуру.
- Поддерживать отдельные окружения разработки, тестирования и production.
- Воспроизводить инфраструктуру.
- Контролировать изменения через Git.
- Автоматизировать развёртывание.
- Управлять ресурсами в рамках инфраструктуры проекта.

## Сравнение трёх подходов

| Критерий | Графический интерфейс | AWS CLI | Terraform |
|---|---|---|---|
| Подход | Управление через интерфейс | Императивный | Декларативный |
| Основной инструмент | AWS Management Console | Команды AWS CLI | Конфигурационные файлы HCL |
| Что задаёт пользователь | Действия и параметры через интерфейс | Команды для выполнения операций | Желаемое состояние инфраструктуры |
| Кто определяет последовательность операций | Пользователь выбирает действия, платформа выполняет их | В основном пользователь или его скрипт | Terraform на основании зависимостей |
| Автоматизация | Ограниченная | Скрипты и программные сценарии | Описание инфраструктуры в коде, интеграция с CI/CD |
| Повторное выполнение | Зависит от выбранной операции | Зависит от команды | Обычно не вызывает изменений при совпадении состояния и конфигурации |
| Предварительный просмотр изменений | Зависит от сервиса | Зависит от операции и скрипта | `terraform plan` |
| Типичные задачи | Исследование и разовые операции | Администрирование и автоматизация операций | Управление инфраструктурой как кодом |
