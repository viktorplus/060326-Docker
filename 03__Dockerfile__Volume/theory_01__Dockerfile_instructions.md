
### 1. Базовый образ и сборка

| Инструкция | Назначение                                   | Пример                    |
| ---------- |----------------------------------------------| ------------------------- |
| `FROM`     | Задаёт базовый образ                         | `FROM python:3.12-slim`   |
| `ARG`      | Переменная, доступная только на этапе сборки | `ARG PYTHON_VERSION=3.12` |

```dockerfile
FROM python:3.12-slim
ARG APP_ENV=production
```

`FROM` практически всегда является первой основной инструкцией Dockerfile.

    Перед ней в файле могут стоять только то, что этапом ещё не является: 
    комментарии, пустые строки, директивы парсера и глобальные ARG. 
    Любая другая инструкция (RUN, ENV, COPY…) до первого FROM — ошибка.


#### `FROM scratch`

`FROM scratch` означает: создать Docker-образ, начиная с полностью пустого базового образа.

```dockerfile
FROM scratch
```

`scratch` — это специальное значение Docker, а не обычный образ.  
Это полностью пустая основа, в ней нет: 
* файловой системы,
* shell, 
* библиотек 
* и других файлов.


##### Зачем это нужно?

Если нужна очень лёгкая программа — самостоятельный бинарный файл.

### 3. Файлы и каталоги

| Инструкция | Назначение                                      | Пример                |
| ---------- |-------------------------------------------------| --------------------- |
| `WORKDIR`  | Устанавливает рабочий каталог внутри контейнера | `WORKDIR /app`        |
| `COPY`     | Копирует файлы из build context                 | `COPY . /app`         |
| `ADD`      | Копирует файлы + умеет распаковывать tar-архивы | `ADD app.tar.gz /app` |


```dockerfile
WORKDIR /app

COPY requirements.txt .
COPY app/ ./app/
```

Так же `WORKDIR` создаёт каталог, если его ещё нет.

Все последующие инструкции Dockerfile будут выполняться относительно этого каталога.

`COPY` также может создать каталог (каталог назначения), если его ещё нет.

### 4. Установка программ и создание образа

| Инструкция | Назначение                                | Пример                                |
| ---------- | ----------------------------------------- |---------------------------------------|
| `RUN`      | Выполняет команду во время `docker build` | `RUN pip install -r requirements.txt` |

```dockerfile
RUN apt-get update && apt-get install -y curl
RUN pip install -r requirements.txt
```

**Важно различать команды `RUN` и `CMD`**:

* `RUN` выполняется на этапе сборки образа, а результат выполнения становится частью создаваемого слоя образа.
* `CMD` — выполняется уже при запуске контейнера.

### 5. Запуск приложения

| Инструкция   | Назначение                                  | Пример                      |
| ------------ | ------------------------------------------- | --------------------------- |
| `CMD`        | Команда и/или аргументы по умолчанию        | `CMD ["python", "main.py"]` |
| `ENTRYPOINT` | Основная программа контейнера (точка входа) | `ENTRYPOINT ["python"]`     |

Обе инструкции задают, **что запустить при старте контейнера**.
Если одну и ту же инструкцию написать несколько раз, действует **только последняя**.


```dockerfile
CMD ["python", "main.py"]
```

---

#### `CMD` vs `ENTRYPOINT`

`CMD` — значение по умолчанию. Его легко заменить аргументами `docker run`:

```dockerfile
CMD ["python", "main.py"]
```

```bash
docker run myapp bash
```

В этом случае запустится `bash`, а не `python main.py`.  
То есть всё, что написано после имени образа, **полностью заменяет `CMD`**.

`ENTRYPOINT` задаёт программу, которая запускается **всегда**.  
Аргументы `docker run` её не заменяют, а **добавляются** к ней:

```dockerfile
ENTRYPOINT ["python"]
CMD ["main.py"]
```

| Как запускаете            | Что реально выполнится |
| ------------------------- | ---------------------- |
| `docker run myapp`        | `python main.py`       |
| `docker run myapp app.py` | `python app.py`        |
| `docker run myapp --help` | `python --help`        |

Чтобы заменить сам `ENTRYPOINT`, нужен флаг:

```bash
docker run --entrypoint bash myapp
```

---

#### Как их сочетать?

Обычная схема:

- в `ENTRYPOINT` — исполняемый файл;
- в `CMD` — аргументы по умолчанию.

```dockerfile
ENTRYPOINT ["python"]
CMD ["main.py"]
```

Так контейнер ведёт себя как программа: 

* его можно запускать "как есть", 
* а при необходимости подставлять другие аргументы, не ломая точку входа.

### 6. Переменные окружения

| Инструкция | Назначение                                             | Пример                   |
| ---------- | ------------------------------------------------------ | ------------------------ |
| `ENV`      | Устанавливает переменную окружения в образе/контейнере | `ENV PYTHONUNBUFFERED=1` |

```dockerfile
ENV PYTHONUNBUFFERED=1
ENV APP_ENV=production
```

В отличие от `ARG`, переменная `ENV` доступна уже при запуске контейнера.

---

### 7. Пользователь и права

| Инструкция | Назначение                                                           | Пример     |
| ---------- | -------------------------------------------------------------------- | ---------- |
| `USER`     | Определяет пользователя, от которого выполняются последующие команды | `USER app` |

Например:

```dockerfile
RUN useradd -m app

USER app
```

После этого приложение будет запускаться не от `root`.

---

### 8. Сеть и порты

| Инструкция | Назначение                                      | Пример        |
| ---------- |-------------------------------------------------| ------------- |
| `EXPOSE`   | Декларирует номер порта для связи с контейнером | `EXPOSE 8000` |

```dockerfile
EXPOSE 8000
```

**Важный момент**: `EXPOSE` сам по себе порт наружу не публикует.

Публикация выполняется, только если пробросить порт специальной командой, например:

```bash
docker run -p 8000:8000 myapp
```

---

### 9. Volumes

| Инструкция | Назначение                    | Пример         |
| ---------- |-------------------------------| -------------- |
| `VOLUME`   | Объявляет точку монтирования  | `VOLUME /data` |

```dockerfile
VOLUME /data
```

Позволяет хранить данные отдельно от файловой системы контейнера.  
Что даёт возможность сохранить эти данные даже при удалении контейнера.
(Особенно важно для контейнеров с БД.)
